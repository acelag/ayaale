## Metadata and indexing policy

- Canonical host is `https://ayaale.com`. Query strings, fragments and campaigns never appear in canonical URLs. `www.ayaale.com` permanently redirects to the apex host. Public-page metadata uses only the approved data already shown on that page.
- Root metadata remains noindex. Public pages may opt into indexing only when `SEO_INDEXING_ENABLED=true`, `APP_ENV=production` and `NEXT_PUBLIC_SITE_URL=https://ayaale.com` exactly, with known preview flags absent. Staging/development stay noindex and disallow crawling. This task leaves the switch off.
- Search/filter/pagination URLs use a homepage canonical with noindex in production; plain homepage and campaign-only variants share the homepage canonical. Search text never enters metadata. Home service errors, inactive offers, missing properties and missing offers remain noindex. Existing authentication and authorization are unchanged.
- Private/account/admin/newsletter routes have noindex metadata and/or response headers. In production their HTML is crawlable so a crawler can read noindex; robots exclusions alone do not remove a URL from search. API and token-redirect endpoints are excluded from crawling. Public approved image routes have specific crawl exceptions so social/search crawlers can read them. Robots directives are not access controls. [Google noindex guidance](https://developers.google.com/search/docs/crawling-indexing/block-indexing)
- Structured data describes the website, actual public business and active offer. Price specifications distinguish exact from starting prices, include LKR, the displayed unit/coverage and tax treatment. No ratings, reviews, booking availability or quality promises are invented. Unavailable offers do not emit Offer markup. Script-breaking characters are escaped before rendering JSON-LD. These schemas describe content; rich-result eligibility or search ranking is not guaranteed. [Schema.org Offer](https://schema.org/Offer), [LocalBusiness](https://schema.org/LocalBusiness)

## Sitemap behavior and security

The sitemap includes the homepage, effectively active approved offers and verified non-archived property profiles, including properties without current offers. It reuses the existing offer eligibility predicate, so suspended businesses, paused/admin-hidden offers, unapproved revisions, expired publication/redemption dates and inactive entitlements cannot enter the offer sitemap. Expiry checks happen at request time, independently of the scheduled lifecycle worker.

The reader uses the public publishable key, keyset pages of up to 1,000 paths, a shared 10-second timeout and a maximum of 50,000 URLs including home. Failed RPCs, malformed/non-monotonic paths or a catalogue exceeding that limit return 503 with Retry-After; a launch-disabled sitemap returns 404. Failures never publish an empty/partial successful catalogue. Larger catalogues require a sitemap index and sharding before that limit. No guessed modification dates are supplied. A live eligibility change during enumeration can still make a URL unavailable before a crawler visits; the destination page's current eligibility remains authoritative. [Google sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)

The privileged projection is confined to the non-exposed discovery schema, has an empty search path and explicit grants, and exposes only existing public paths. No table access, auth-role changes or subscriber information are added. Local anonymous-role tests verify the projection. Hosted verification succeeded as `anon`; the current development catalogue returned zero public paths, so an enabled sitemap would contain only home until eligible listings exist.

The hosted security scan added no findings. Its pre-existing private-schema deny-all notices and existing leaked-password-protection warning remain unchanged; no plan was upgraded. [Supabase advisor explanation](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy), [password protection setting](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

## Search Console setup and launch checklist

1. In [Google Search Console](https://search.google.com/search-console/), add the `ayaale.com` Domain property and use the exact DNS TXT record Google supplies, or add the URL-prefix property `https://ayaale.com/` and select HTML tag verification. No record or verification token is fabricated. Domain verification requires DNS; the HTML tag verifies only the selected URL-prefix property. [Google ownership verification](https://support.google.com/webmasters/answer/9008080)
2. For HTML verification, put only the tag's `content` value into server environment variable `GOOGLE_SITE_VERIFICATION`, then rebuild/redeploy the canonical production configuration. The code renders the tag only when `APP_ENV=production` and the site origin is exactly `https://ayaale.com`; it works independently of optional GA consent and the indexing switch. Confirm the tag in the homepage's server HTML before selecting Verify. Keep it deployed after verification. For DNS, keep the supplied TXT record instead.
3. Keep `SEO_INDEXING_ENABLED=false` until launch content, legal notices and production readiness are approved. Preview copies must keep their own non-production environment settings; the environment gate cannot compensate for incorrectly labeling a preview as production. No public launch was performed in T050.
4. At the approved launch, set `SEO_INDEXING_ENABLED=true` with the canonical production settings, rebuild/deploy and check `/robots.txt`, `/sitemap.xml`, one approved offer and one verified property. Inspect the www redirect and ensure public image URLs are accessible. Indexing-disabled images also remain noindex.
5. Submit `https://ayaale.com/sitemap.xml` in Search Console, use URL Inspection on a small set of approved canonical pages and review the Page indexing report. Check that private/expired/filter variants stay excluded. No verification, sitemap submission or ranking result is claimed until those account-side actions are completed.
