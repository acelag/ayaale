# T012 — Expanded authorization tests

## Outcome and files

Created tests/database/authorization.test.mjs and this delivery record; updated README, task board, blueprint and testing guide. No production code, migration, schema, grants, dependency or hosted configuration changed. Existing CI already includes the new file through npm run test:db.

The new isolated suite seeds two properties with different owners, one staff member assigned to both and another assigned only to the first. Fixtures include approved published offers, revision/status history, nonzero aggregate metrics, verification proposals, subscriptions/trials, reporter contacts, subscriber consent/token records, raw events, notifications, email logs and a platform admin. All fixtures are synthetic and exist only in a randomly named disposable local database.

## Tests and acceptance criteria

Sixteen cases prove:

- [x] Staff cannot enumerate unassigned properties through list reads, explicit UUID filters, membership reads or role helpers.
- [x] Another property's offers, revisions, history and aggregate metrics remain hidden; assigned data is readable.
- [x] Explicit multi-property staff assignments work without granting owner permissions.
- [x] Different owners see only their own subscription, trial and verification evidence.
- [x] Staff cannot read these owner-only records even for their assigned property.
- [x] Owners/staff cannot read populated reporter contacts, subscriber/consent/token data, raw events or email logs.
- [x] Notifications remain recipient-scoped, including among members of the same property.
- [x] Staff cannot self-promote, create/delete memberships, transfer ownership, change billing/trials, verify properties or approve revisions.
- [x] Generic direct offer writes remain denied pending task-specific trusted workflows.
- [x] Self profile-name editing works; other-profile edits affect zero rows, ID changes and admin self-assignment are denied.
- [x] Forged role metadata does not override database memberships/admin assignments.
- [x] Membership removal, ownership transfer and admin removal revoke database reads without a token refresh.
- [x] Unconfirmed and independently banned identities lose assigned data and notification reads.
- [x] Anonymous/missing-subject identities do not inherit authenticated data/helper access.

Negative SQL checks assert permission-denied SQLSTATE 42501 or empty RLS results as appropriate, with savepoints so an aborted transaction cannot masquerade as a later successful denial. Positive controls verify records exist and authorized reads work. Per-case transactions roll back mutations.

## Security considerations and limits

Tests use PostgreSQL authenticated/anon roles and synthetic Auth UID context. Only the test administrator sets these contexts; real callers cannot choose another JWT subject without a valid signed token. The metadata case proves role decisions ignore injected role fields; it is not a JWT-signature penetration test. Real Auth email delivery, HTTP/session-cookie behavior and end-to-end signup remain separate from these database tests.

No new grants are opened to make tests pass. Private data is tested with populated rows, avoiding empty-table false positives. Test connection validation rejects hosted databases; the harness creates/drops only its own randomly named local database. No hosted migration or rollback is applicable.

Current clients intentionally lack generic property/offer/team/billing mutation rights. This suite tests those denials, not completion of future owner invitation or staff offer-management workflows. Later authorized actions must test both server guards and RLS when implemented. T014 session revocation/abuse controls, T024–T027 signup/invitations, and later task-specific mutations remain separate. Browser regressions were not repeated for a test/document-only change; the 12 T011 production browser checks remain the latest result.
