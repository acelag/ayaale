## Schema and storage

The ayaale-private-photos bucket is private, permits WebP only and caps individual processed objects at 2 MiB. No Storage object policy grants browser reads/writes. Direct uploads, overwrites and signed-upload URLs are deliberately unavailable, so clients cannot bypass server validation. Server storage access requires SUPABASE_SECRET_KEY, never a NEXT_PUBLIC_ value.

public.photo_assets stores property/uploader IDs, generated main/thumbnail paths, dimensions, bytes and timestamp. RLS allows assigned members/admins to read metadata, with anonymous reads and client mutations denied. Paths must match the exact property/asset UUID layout; dimensions and byte sizes are bounded. Indexed FKs protect association integrity. The migration was generated with the checked Supabase CLI, locally replayed, applied to development and aligned to the returned hosted version. Previous migrations are unchanged.

Assets remain private drafts, not approved public content. Property/offer photo ordering, alt-text editing, gallery UI, reviewed snapshot binding and public delivery belong to T026/T028/T037 and public-page tasks. Never expose draft assets merely because an object exists. Current read URLs expire after 60 seconds and require current property membership before issuance; possession of an issued URL grants access until it expires, even if membership is subsequently removed.

## Upload contract and security

POST accepts the raw image body with exact Content-Type image/jpeg, image/png or image/webp and an Origin matching NEXT_PUBLIC_SITE_URL. It validates a property UUID and confirmed property membership before reading bytes, then rechecks authorization after decoding. No filename or caller-chosen object path is used. Streaming counts actual bytes without trusting Content-Length, cancels above 8 MiB and never writes originals to application disk.

Defaults chosen for T013 because the specification supplies no numeric limits:

| Check/output  | Limit                                                                |
| ------------- | -------------------------------------------------------------------- |
| Input         | 8 MiB; JPEG, PNG or WebP                                             |
| Decode        | 24 million pixels; maximum 12,000 on either dimension                |
| Minimum input | 240 pixels on both dimensions                                        |
| Animation/SVG | Rejected                                                             |
| Main          | Fit inside 1600×1600, no enlargement, WebP quality 82, at most 2 MiB |
| Thumbnail     | Fit inside 480×480, no enlargement, WebP quality 76, at most 512 KiB |

Sharp verifies actual decoded format against the declared type, fully decodes/re-encodes, applies EXIF orientation and strips metadata. Corrupt/truncated/unsupported files fail closed. Originals, EXIF and arbitrary browser-provided paths are never persisted. Uploads use generated UUIDs with upsert=false. Failed writes attempt object cleanup; process crashes can still leave orphaned objects because Storage and PostgreSQL are not one transaction. A future reviewed reconciliation/retention job must remove unreferenced objects safely; no such job is claimed.

Both variants must upload before the asset record is inserted. The GET route scopes the record to the requested property before issuing short-lived signed URLs. Responses are private/no-store; raw provider errors and credentials are not returned. No global privileged client session is retained. A missing secret returns 503 after authorization. Rate limiting, quota enforcement, decoder concurrency controls and broader abuse protections remain T014 and are release gates before unrestricted uploads; Storage/free-tier limits still apply.
