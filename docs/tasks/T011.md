## Behavior and access matrix

| Identity                     | Access                                                                                    |
| ---------------------------- | ----------------------------------------------------------------------------------------- |
| Anonymous/unconfirmed/banned | No application data                                                                       |
| Verified user                | Own profile; plan catalogue                                                               |
| Assigned owner               | Assigned property/team/offer data, private verification and subscription/trial reads      |
| Assigned staff               | Assigned property/team/offer data and aggregate metrics; no billing/verification evidence |
| Platform admin               | Cross-property reads and private operational reads                                        |

Notification reads are recipient-scoped or admin. Raw reports, subscriber addresses/consent/tokens, raw events and delivery logs are admin-only. Profiles allow only verified self creation and display-name updates; IDs/roles cannot be updated. All direct property, membership, verification, subscription and offer mutations stay denied to authenticated clients: later task-specific server workflows must authorize and validate writes rather than opening generic privileged updates. Admin read access does not itself grant generic DML. Private schemas remain unexposed to REST; future safe server projections/RPCs are required for private reads, not exposure of the entire schema.

Platform admins live in private.platform_admins, with no runtime admin-assignment grant. Bootstrap a confirmed, independently verified operator through reviewed database SQL; no admin was assigned in this task. Never derive roles from raw_user_meta_data. Owners/staff remain explicit per-property memberships from T007.

Three private SECURITY DEFINER read helpers are narrowly justified: Auth confirmation/ban lookup and role reads would otherwise require exposing Auth/private rows or recursive membership policies. Helpers have empty search paths, no caller-supplied user IDs and bind all lookups to auth.uid(); browser EXECUTE is revoked except authenticated access needed for policies. No mutation occurs through them. The public admin-check wrapper is SECURITY INVOKER and returns only the current caller's boolean.

## Auth integration and security

Cookie-based PKCE clients use only the public publishable key. Proxy refreshes claims on auth/partner/admin paths and carries refreshed cookies and SDK cache headers. Server guards call getUser for fresh identity, require confirmed email and reject anonymous Auth users; property role/admin checks use current database state. No getSession authorization or user metadata trust. Membership/ban revocation takes effect in database reads. Supabase JWTs may survive logout until expiry; sensitive future writes need current-session validation/revocation requirements reviewed in T014, not a claim that logout invalidates every token immediately.

Server actions implement signup, signin, signout with generic account messages and bounded email/password inputs. Signup always requests the configured site's fixed callback; callback exchanges a PKCE code and always returns to / (no caller-controlled redirect). Auth responses are private/no-store and referrer-free. Confirmed signin creates a missing own profile without overwriting existing display names. Use the server client from writable-cookie route/action contexts; future rendering should rely on proxy refresh and a dedicated read-only adapter if necessary.

Live development Auth settings report email confirmation required. No real signup, email, password, provider secret or administrator assignment occurred. End-to-end inbox delivery, redirect allowlist and customized templates require the actual T024 signup UI/operator inbox; these are explicitly unverified. Supabase's built-in development sender limits remain unchanged. No custom SMTP or paid service was enabled. Auth UI, reset-password screens, invitations, registration and property mutation workflows remain T024–T027 and later. Signup abuse controls/rate limiting and broader audit/recovery remain T014.
