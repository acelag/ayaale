# T053 — Continuous onboarding-to-duplicate journey

A continuous browser journey now follows one newly registered property through signup/confirmation, independent admin verification, six-month trial allocation, draft save/resume/preview, offer approval/publication, contact, expiry and duplication. It runs against the actual migrated PostgreSQL database through the production Next.js pages and server actions. Desktop Chromium and iPhone-profile WebKit are both covered.

All state is synthetic and lives in a randomly named disposable loopback database. No hosted project, real business, trial allocation, email, WhatsApp account or phone call was touched. T053 adds tests and their local harness only; no application/schema change or deployment is required. The earlier T051/T052 working-tree changes remain intact and unpublished. T054 is not started.

## What the journey verifies

1. **Onboard:** submit signup through the actual form and exchange the test provider's PKCE confirmation code through `/auth/callback`. Register a new property through the actual server action, confirm pending status and zero trial allocations, then upload and process a synthetic photo.
2. **Verify and allocate trial:** a separate admin browser session supplies existence/authority checks, an independently confirmed map, location, method and evidence. The real verification RPC allocates exactly one trial. Its period is checked as six Sri Lanka calendar months; the partner sees Free trial active.
3. **Draft:** save a partial draft, leave and resume that exact draft, complete the wizard, select the uploaded cover and verify its signed preview actually loads. Submit through the real action. The database contains one pending-review offer with no first-publication timestamp, and its public URL is unavailable.
4. **Approve and publish:** the separate admin checks the offer and approves the same revision. Real triggers publish it under the property's entitlement. Its active state, approved revision and first-publication timestamp are checked. An anonymous visitor finds it in discovery and opens the correct public details.
5. **Contact:** verify the approved telephone destination. Click WhatsApp, intercept its external popup locally, and confirm the actual contact ingestion endpoint writes one private click event. The trial count and original dates remain unchanged. No real external contact occurs.
6. **Expire:** a strictly test-only control advances the approved revision's publication deadline inside the disposable database, without setting offer status. The public projection already returns ended at the cutoff. The real service-only lifecycle job transitions the offer once to expired, and a retry makes no additional expiry transition. The old URL returns a clear ended page without contact CTAs, discovery removes the offer and the partner sees the freed active slot.
7. **Duplicate:** use the real partner Duplicate button on the expired offer. It creates a different private wizard draft, preserves the title and clears all four publication/redemption dates. The original expired offer, contact history and single original trial remain intact; duplication does not create another public offer or trial.

The test carries the same property/offer IDs through every stage. The adapter does not return canned business outcomes: authorization functions, RLS, request budgets, mutations, review checks, entitlement calculations, audit/status history and public projections execute in PostgreSQL. Each request uses a separate pool lease/transaction so role or JWT-subject settings cannot leak between concurrent requests.

## Substitutes and limitations

- Supabase Auth delivery/session endpoints use the existing local fixture. The app's PKCE verifier exchange, callback, cookies, confirmed-user gates and role-scoped database workflows are exercised, but no real signup email, inbox link, Auth deployment configuration or external provider is validated. This does not close earlier live inbox/email-delivery prerequisites.
- Object bytes use an in-memory private storage substitute; actual upload decoding/compression, database photo assignments, signed preview requests and public cover lookup execute through application code. This does not validate hosted Storage policies, network failures or provider availability.
- Expiry is accelerated through a named local control rather than waiting seven days. Only the publication deadline is adjusted, with immutable-row triggers bypassed for that fixture timestamp change. Status transitions, public eligibility and expiry history still use real application database functions. This control is not a product route, is never added to the deployed Next.js app and cannot run against a hosted URL.
- The adapter implements only the REST calls needed for this journey, not the complete PostgREST or Supabase Auth protocol. An actual hosted-provider smoke test remains a separate release check.
- iPhone WebKit is engine/device-profile emulation. The physical iPhone baseline recorded in T052 covers the earlier live build and is not evidence that this new local journey ran on a physical device.

## Commands

Use the pinned Node 24 runtime and a disposable PostgreSQL cluster with the `ayaale_test` base database:

```sh
npx playwright install chromium webkit
npm run check
AYAALE_TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:54329/ayaale_test npm run test:journey
git diff --check
```

The existing helper rejects hosted hosts, any base database other than `/ayaale_test`, and query/fragment overrides before connecting. The gateway listens only on `127.0.0.1:3101`; Next.js listens on `127.0.0.1:3100`. Run build-backed browser suites sequentially because they share `.next` and these ports. CI supplies its own synthetic PostgreSQL URL and installs matching Chromium/WebKit binaries.

`test-results/journey/` and `playwright-report/journey/` contain failure traces/screenshots and the attached `journey-checkpoints` JSON. The checkpoints record synthetic database state at each successful phase, including trial dates, offer/revision IDs, event counts and RPC outcomes. CI is configured to retain this evidence for three days; no remote CI execution is claimed for unpushed changes.

## Security and verification

The adapter accepts only fixed test API keys, a fixed RPC allowlist and validated SQL identifiers; values use query parameters. Normal app requests run under their actual PostgreSQL role with a transaction-local authenticated subject. Privileged state inspection/time acceleration requires the local test-control header and a property registered by this test gateway. Storage substitutes enforce their test service key or a short-lived issued signed token. No unrestricted SQL, production route, hidden test bypass or new user privilege is introduced in the application.

The journey server is explicitly configured for SIGTERM with a 10-second graceful-shutdown window; this closes the pools and drops only the helper-created database. SIGINT and setup failures also attempt cleanup. Playwright defaults to force-killing web servers, which initially bypassed cleanup and left disposable test databases during test development. Those exact databases were removed, and the final graceful-shutdown run was checked for leftovers. A crash or forced SIGKILL can still require explicit cleanup of its own test database. See [Playwright web-server shutdown](https://playwright.dev/docs/test-webserver). The initial test development exposed a mismatched District selector and missing required map evidence in the new scenario. Both were corrected in the test input/selector; the production approval requirements were preserved. No business-logic fix was needed.

Final verification: both continuous journeys passed on desktop Chromium and iPhone-profile WebKit. Formatting, lint, TypeScript, 36 unit cases, 20 contrast pairs and diff checks passed. The disposable database cleanup was checked after the run.
